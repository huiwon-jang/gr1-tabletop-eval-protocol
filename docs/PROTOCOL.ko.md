# RoboCasa Kitchen 뷰-스왑 프로토콜 (한국어 요약)

영문 전체: [PROTOCOL.md](PROTOCOL.md).

## 무엇이 깨지나

Kitchen 스윕은 24 task × 5 env lane × 10 episode = 1,200 에피소드다. GPU 하나에서
5개 lane을 동시에 돌리는(각자 EGL 컨텍스트를 갖는) 구성이라야 하루 안에 끝난다.

그 구성에서 일부 프레임이 **다른 카메라의 것으로 바뀌어** 렌더된다. 세 카메라
(`agentview_left` / `agentview_right` / `eye_in_hand`)가 서로 내용을 주고받고,
그 교환이 **매 프레임 교대로** 일어난다.

| 통계 | 오염 에피소드 | 정상 |
|---|---|---|
| lag-1 인접 상관 | 0.35 – 0.47 | > 0.9 |
| lag-2 상관 | 0.65 – 0.82 | > 0.9 |

프레임 *t*가 *t+1*보다 *t+2*와 더 닮았다는 것이 서명 전부다 — 두 소스를 교대로
오가고 있다는 뜻이다. 매핑을 복원하면 wrist ← right, left ← right, right ← left이고
(상관 0.72–0.84), 일부는 BGR로 채널까지 뒤바뀐다.

처음에는 로봇 base가 발산하는 것으로 오진했다. lag-1과 lag-37(둘 다 홀수)만 보면
주기-2 교대는 통째로 가려진다. 짝수 lag을 봐야 드러난다.

## 녹화가 아니라 정책 입력이 오염된다

녹화 래퍼와 정책은 같은 observation dict를 쓰지만 **읽는 방식이 다르다**:

- mp4는 `obs.items()` 순회로 만들어진다 — **위치 기반**
- 정책은 키 이름으로 찾는다 (`video.res256_image_side_0` → `left_view` …)

녹화기만의 결함이라면 위치 기반으로만 나타나야 한다. 실제 오염은 두 경로 모두에서
카메라 *내용*을 따라가므로, 정책이 받은 텐서가 이미 틀린 것이다. 추출 forward에
직접 계측을 걸어(롤아웃 중 velocity를 덤프해 `x0 = latents − v`를 VAE 디코드)
확인했다 — 렌더된 파일이 아니라 실제 입력 기준이다.

## 탐지 규칙

어려운 부분은 깨진 프레임을 찾는 게 아니라 **빠르게 움직이는 로봇을 안 잡는 것**이다.
kitchen 정책은 이동 base를 몰기 때문에, base가 크게 흔들리면 픽셀 차이가 깨진 프레임만큼 커진다.

가르는 축은 **매크로 연속성**이다. 각 프레임을 16×16으로 줄여 인접 상관을 본다:

| | 인접 매크로 상관 |
|---|---|
| 실제 운동 (빠른 base 포함) | 0.95 – 0.999 |
| 오염 프레임 | 0.34 – 0.51 |

그래서 규칙은 둘 중 하나면 격리한다: `gap > 0.12` (주기-2 서명), 또는
`med > 20` **이면서** `lag1m < 0.7` (지속적 큰 변화 + 매크로 비연속 = 비물리적).

**일부러 안 잡는 것**: 매크로 연속성이 유지되는 한 base·팔의 빠른 운동, 그리고
40프레임 미만 에피소드. `terminate_on_success` 때문에 정상 성공이 16프레임(=1 action
chunk)일 수 있고, 이걸 손상으로 오판하면 매 cycle마다 같은 에피소드를 다시 격리해
**영원히 수렴하지 않는다**. repair 루프가 안 끝나면 이것부터 확인할 것.

**같이 잡히지만 성격이 다른 것**: `undecodable`. ffmpeg 오류 은닉(error concealment)이
그럴듯한 프레임을 만들어내므로 픽셀로는 판정할 수 없고 stderr로 잡는다. 아래 §마지막 참고.

## 측정값

19개 체크포인트 트리, 22,800 에피소드를 `N_ENVS=5`로 스캔:

| | |
|---|---|
| 격리 | 538 / 22,800 = **2.36 %** |
| `N_ENVS=1` repair 후 재스캔 | 39 / 19,200 = **0.20 %** |
| … 무관한 파일손상 1건 제외 | **1 / 19,200** |

수렴까지 간 16개 트리:

| | |
|---|---|
| 재실행 에피소드 | 433 |
| 결과가 바뀐 것 | 174 (40 %) |
| 평균 성공률 | 60.99 % → 61.86 % |
| 트리별 | 중앙 +1.00pt, 최대 +1.50pt, 16개 중 15개가 상승 또는 동일 |

즉 오염을 그대로 두면 **약 1점**을 잃는다. 방향이 계통적이다 — 뒤섞인 뷰를 받은
정책은 실패하니까 — 하지만 어느 에피소드가 깨지는지는 런마다 달라서 비교가 무너진다.

## 배제한 대안들

애초에 렌더러를 고치는 게 낫다. 250 에피소드로 세 가지를 시험했다:

| 변형 | 지속형 | 스왑 서명 | 성공률 |
|---|---|---|---|
| 무수정 | 8 | 4 | 132/250 = 52.8 % |
| 렌더 전 `make_current` | 11 | 6 | 133/250 = 53.2 % |
| 렌더 후 검증·재시도 | 5 | 4 | 132/250 = 52.8 % |
| **`N_ENVS=1`** | **2** | **2** | 126/250 = 50.4 % |

EGL 컨텍스트를 매 렌더마다 명시적으로 바인딩해도 안 되고, 검증·재시도는 처리량을
크게 깎으면서 절반만 줄인다. 오직 env 1개만 남기는 것이 스왑을 없앤다. 오염이
소수이므로, **그 소수만** `N_ENVS=1`로 다시 돌리면 단일 env의 정확도를 동시 실행의
처리량으로 얻는다.

mujoco 3.3.x 업그레이드도(진행 중인 다른 평가가 영향받지 않게 kitchen 전용 v2 환경을
따로 만들어) 확인했으나 스왑은 해결되지 않았다.

## append 사고 — 반드시 읽을 것

repair는 시드를 맞추려고 `ENV_LAYOUT=5`를 유지한 채 `N_ENVS=1`로 돈다. 그런데
빈 인덱스를 채우는 hole-aware resume이 `n_envs > 1` 로만 게이트돼 있어서 repair가
그걸 건너뛰고 lane 상한 뒤에 ep10, 11, 12…를 **덧붙였다**. 트리가 1,200을 넘고,
repair 대상이 아니던 **이미 보고된 성적이 바뀌었다** (67.8 → 68.0, 65.1 → 64.8).

`patches/01-hole-aware-resume.patch`가 게이트를 `n_envs > 1 or env_layout > 0`으로
넓히고 eval 스크립트에서 `--env_layout`을 넘긴다. **이 패치 없이는 repair를 돌리지 말 것.**
repair 후에는 `_quarantine_swap/`을 제외한 트리가 정확히 1,200인지 확인한다.

## cycle

repair 자체도 평가라 새 오염이 생길 수 있으므로 끝난 뒤 다시 스캔한다. 측정 결과
2회차까지 간 16개 트리 중 **14개가 0**이었다. 스캔 → repair → 스캔, 0이면 종료,
2회차에서 뭔가 나올 때만 3회차. 기계적으로 3번 돌 필요는 없다.

`swap_cycles.json`이 각 cycle 진입 시점 상태를 갖고 있어 `원본 → 1회차 → 최종`을
그릴 수 있다. **`_quarantine_swap/`을 지우지 말 것** — 이력 파일이 생기기 전에
repair된 트리는 격리된 파일명이 원본 성패의 유일한 기록이고, 스캐너가 그걸로 cycle 1을
복원한다.

## `undecodable`에 대한 단서

성공/실패 라벨은 환경이 파일명에 쓰는 것이지 비디오에서 읽는 게 아니다. 따라서 mp4가
깨졌다는 건 *녹화*가 실패했다는 뜻이지 *관측*이 오염됐다는 증거가 아니다. 그걸 재실행하면
멀쩡할 가능성이 높은 라벨을 버리고 새로 뽑는 셈이고, 추출 노이즈가 시드 고정이 아니라
같은 장면이라도 결과가 달라진다.

데이터가 이를 보여준다. 격리된 것이 전부 `undecodable`이었던 트리 하나는 repair 후
−0.17pt(6개 재실행, 2개 뒤집힘)였고, 스왑이 주류인 트리는 전부 올랐다. 이 구분이
중요하다면 `reason`으로 걸러 `swap-alt`와 `sustained-nonphys`만 repair하면 된다.
